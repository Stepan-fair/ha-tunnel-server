# Модель безопасности и границы проверки

Версия 0.1.0 пока не готова для постоянной публичной эксплуатации. Равенство безопасности CloudPub не доказано сравнительным аудитом. Цели реализации: обязательный TLS, индивидуальная аутентификация, изоляция доменов, ограниченные административные поверхности и отзыв действующих соединений.

## Доверенные компоненты

- Владелец Server, HA OS, Supervisor и Nginx Proxy Manager на серверной стороне. NPM завершает браузерный HTTPS и видит трафик. Компрометация этой стороны даёт доступ к содержимому проксируемого трафика.
- Администраторы клиентского HA; Client имеет доступ к конфигурации, право проверки/перезапуска Core и административный Core API через Supervisor (`homeassistant_api`). Пользовательский токен не требуется.
- Публичная Web PKI при первоначальной выдаче кода и получении OIDC-токенов. CA туннеля закрепляется из проверенного HTTPS-ответа, имя сервера проверяется.
- DNS-провайдер и контроль домена: DNS-01 для wildcard должен иметь отдельный минимально привилегированный доступ, где поддерживается провайдером. Секрет DNS не передаётся клиентам.

## Защита

Код и постоянный секрет содержат 256 случайных бит. Код хранится как SHA-256 и AES-GCM шифротекст с отдельным ключом в `/data/state/invitations.key`, одноразово обменивается в SQLite-транзакции, живёт 900 секунд. Постоянный секрет хранится на Server только как SHA-256. OAuth2 client_credentials выдаёт RS256 JWT на час; `sub` и поколение привязки проверяются на Login, Ping и NewWorkConn. Login нормализует поколение в session metadata, NewProxy сверяет его. Старый JWT без поколения действует только для исходного поколения0.

Политика FRP разрешает ровно назначенный домен и каноническое имя HTTP-прокси; неизвестные поля, группы, маршруты, подмена host и произвольные типы запрещены. Отказ при недоступности обработчика подтверждён интеграционным сценарием с настоящим FRP 0.71.0.

Пауза и отзыв сохраняются до принудительного прерывания транспорта выбранного клиента через контролируемый loopback relay; медленный получатель не задерживает отключение других клиентов. Повседневные команды не перезапускают общий frps. Relay проверяет Host, однозначность framing и один HTTP-запрос на соединение; raw WebSocket разрешён только после настоящего101. Один JWT без действующей разрешённой записи клиента недостаточен.

После перепривязки Server назначает внутренний FRP Host текущему поколению, а relay использует именно этот маршрут. Старый заранее авторизованный FRP pool остаётся на прежнем маршруте и не получает новые запросы; HA получает прежний публичный Host. Клиент не выбирает внутренний маршрут. Login также назначает случайный nonce сеанса: запоздалый CloseProxy не удаляет публикацию нового сеанса. Ожидаемая идентичность при замене кода проверяется внутри транзакции до погашения: чужой код не изменяет другого клиента.

Отдельный HTTPS status scope разрешает читать только собственные публичные показатели даже при паузе или отзыве, не выдаёт токены туннеля и коды. Повторная привязка заменяет и этот секрет. MQTT не содержит кодов/секретов; кнопки используют ревизию и nonce текущего процесса. MQTTv5 RAP и retainHandling2 плюс проверка retain-флага запрещают сохранённые команды, включая публикацию при уже активной подписке. QoS1 повтор защищён долговременным command_id. Сервисные MQTT-учётные данные Supervisor могут иметь широкие grants; ACL брокера и администраторы HA остаются доверенной границей, независимая изоляция между приложениями не обещается.

Публичный listener не содержит административных маршрутов. NPM проверяется по фактическому IP источника. Заголовки forwarded нормализуются в шлюзе. Ingress проверяет источник, ID пользователя и CSRF. Для Server используется явный список ID; Client проверяет действующих администраторов в HA auth storage. Обычному пользователю HA доступ к управлению туннелем не предоставляется.

## Секреты и восстановление

Секреты только в `/data`, права файлов 0600. Не включать каталог в Git, журнал или диагностику. Ответы регистрации не кэшируются, редиректы не принимаются. Прямые журналы FRP намеренно отбрасываются; сообщения приложения не содержат тела запросов или исключения с секретами.

Копия состояния шифруется AES-256-GCM, ключ выводится из отдельного пароля через scrypt (N=16384,r=8,p=1). Восстановление проверяет структуру и создаёт чистую БД из проверенных строк, не исполняя SQL из архива. Восстановление старой копии возвращает состояние отзывов на дату копии: после аварийного восстановления повторно отзовите клиентов, отключённых позднее.

## Ограничения первой версии

Изменение YAML проверяет хеши основного файла и include непосредственно перед атомарной заменой; собственные записи сериализованы. Это обнаруживает изменения во время подготовки/сохранения копии, но не является файловой транзакцией с произвольным внешним редактором: остаётся короткое окно между последней проверкой и заменой. Не редактируйте те же файлы одновременно с мастером; при необходимости подготовьте HTTP вручную. Копия содержит версию, проверенную мастером, а не гарантированно последнюю версию независимого редактора.

Нет защиты канала от объёмной DDoS-атаки; предел задают ресурсы сервера и провайдера. Ограничение запросов API действует в памяти и сбрасывается при перезапуске. Блокировка endpoint protection в Windows не обходится: сквозные FRP-тесты должны запускаться в отдельном Linux-контейнере. Контейнерные сборки, внешний CGNAT, Companion, реальные forwarded headers и автоматическое продление внешнего сертификата требуют приёмки.

Зависимости Python закреплены по версиям, базовый multiarch-образ закреплён digest, архивы FRP проверяются SHA-256. Debian-пакеты устанавливаются из официального репозитория на момент сборки; их точный набор должен фиксироваться при выпуске проверенного образа. Не считать исходный Dockerfile бит-в-бит воспроизводимой опубликованной сборкой.
