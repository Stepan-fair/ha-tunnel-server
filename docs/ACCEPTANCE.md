## Измерение ограниченного стенда

Сравниваются application sources публичной базы `dce6378b7175ca30ee0d1bff68c27b74ba3c9a77` и текущей версии в одном developer runtime; это не измерение старого образа 0.4.3 или финального production runtime. Локально Windows/Python 3.14.5, aiohttp 3.14.3, cryptography 50.0.1, Paho 2.1.0; отдельная locked проверка использует aiohttp 3.14.5 и cryptography 50.0.2. Loopback, 112 ответов по 4 с, максимум 8 workers и 224 authenticated status запроса с одного IP. Нагрузка прекращается при заданном времени/пределе очереди; production не используется.

База: первый полный обход 57.574 с, первый повтор 72.631 с, p95 status 7.804 мс, CPU процесса на фазе telemetry 2.828 с. Текущая версия: обход 57.602 с, повтор 57.603 с, p95 9.662 мс, CPU 6.516 с. Обе дали 224 ответа HTTP 200: разделение authenticated status budget уже было в базе. Старые показания базы остаются значением после 50 с; текущая версия показывает неизвестное. Первый повтор измеряется отдельно и может начаться до окончания последней проверки полного обхода.

MQTT базы остановлен на measurement cap после 500 попыток: 10023 Paho messages, 10000 callbacks → 10000 handoffs за 90.65 мс, RSS 55,963,648 → 92,827,648 bytes. Новый bounded outbox удерживает 20 pending/20 Paho при 510 попытках и сводит 10000 callbacks к одному handoff за 3.888 мс, RSS 56,238,080 → 57,163,776 bytes. Цена защиты включает дополнительный CPU и задержку обработки status; нельзя считать все пути быстрее. RSS — рабочий набор процесса, telemetry следует после MQTT и включает удержанную им память; один прогон не является гарантией ёмкости.

SHA256 application sources измерения: база `12c49930fd04a48b17a6a67cc4609e91a8bd9b3970a1d9c8f42d437edc319ead`, текущая версия `c8d451c9ac7971b1f1712be0aa189ea462368fb2b6dfb9776ff71fa5a1c5162b`. Последующие изменения исходников требуют явно указанной повторной проверки соответствующей части.

После запрета неподдерживаемого MQTT proxy и исправления перехода с зависшего IPv6 на IPv4 повторена только затронутая MQTT фаза: SHA256 `f1d004dfafa638e256cdc13ba1545fe7fc6cadeef052299dce1072cc9b62e2b3`, 510 попыток, Paho/pending/wire по 20, 10000 callbacks → один handoff за 3.762 мс, RSS 55,382,016 → 56,332,288 bytes, CPU 0.547 с против 0.172 с базы. Telemetry выше относится к прежнему указанному source SHA; её код этими изменениями не изменён.

Реальное сравнение FRP выполняется в существующем Linux security job: восемь clones, 768 MiB, 2 CPU, 256 pids, без внешней сети, текущие patched FRP/dependencies для обеих application policies. Frozen public baseline монтируется read-only отдельным checkout; production image строится в другом job со свежим checkout. Измеряются принятые controls по фактическим sockets, CPU/RSS и счётчики surviving peer. На момент этой записи финальный Linux прогон ещё не выполнен.

До выпуска требуются независимое whole-branch review, финальные Linux zero-skip проверки обеих ролей, exact OCI/smoke/SBOM/scan/registry readback, установленный digest, сохранность состояния и внешний CGNAT HTTPS/WSS. Длительная Companion сессия, недоступные владельцу Client и физические отключения не объявляются проверенными по локальному стенду. Специальное восстановление Server при полном диске и автоматические backup space/schedule/retention исключены из этого выпуска.

## Обязательные внешние сценарии

1. Подключить два независимых HA, получить разные адреса без индивидуальных DNS/NPM-правок.
2. Проверить HTTPS-цепочку, вход HA, WebSocket, обновления состояний, Companion и длительную сессию.
3. Подделать X-Forwarded-For/Host/Proto со стороны браузерного запроса; убедиться, что HA получает нормализованные значения и настоящий внешний адрес.
4. Отозвать первый Client во время активного WebSocket. Его соединение закрывается и не возвращается; второй Client автоматически восстанавливается.
5. Перезапустить Server и Client, проверить сохранение привязки и запрет повторного кода. Отключить туннель и проверить локальный HA.
6. Проверить недоступный DNS/сервер и неверное время/сертификат. Клиент не отключает проверки TLS ради восстановления.
7. Выполнить контролируемое продление wildcard-сертификата и отдельный перевыпуск внутреннего leaf; подтвердить восстановление клиентов без нового кода под прежней CA.
8. Из интернета и обычного LAN проверить недоступность панелей, OIDC discovery, FRP policy и внутренних HTTP-портов.

Только после фиксации результатов всех обязательных сценариев можно менять статус готовности.
