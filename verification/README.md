# HA Tunnel — Server и Client для HA OS

Server и Client устанавливаются отдельно. Инструкции с нуля: [Server](docs/SERVER_INSTALL.md) и [Client](docs/CLIENT_INSTALL.md). Server при новой установке открывает защищённый мастер без заранее заданного домена; настройки существующей установки сохраняются. Публичные репозитории новой версии: [Server](https://github.com/Stepan-fair/ha-tunnel-server), [Client](https://github.com/Stepan-fair/ha-tunnel-client). До выпуска и приёмки новой версии действующая установка продолжает использовать прежний источник.

Два приложения для удалённого доступа к Home Assistant за CGNAT через собственный сервер с белым IP. Server выдаёт одноразовый код и отдельный HTTPS-адрес; код вставляется в Client. Лицензионного ограничения на пять домов нет.

**Server 0.3.1 / Client 0.3.1 установлены из раздельных публичных репозиториев.** Живой перенос, журнал после перезапуска, таймер и восстановление после отзыва проверены. Штатное ручное обновление 0.3.0 → 0.3.1 прошло; автообновление включено, фактический запуск по расписанию ещё не проверен. Индивидуальная пауза, календарные сроки, повторные коды и MQTT-сущности подключения. Client сохраняет штатную настройку HTTP в HA2026.8+ с подтверждением после перезапуска. Полная [приёмка](docs/ACCEPTANCE.md), включая Companion, второй живой клиент, arm64 и продление сертификата, ещё не завершена.

## Как это устроено

Браузер → HTTPS в Nginx Proxy Manager → Server → TLS-туннель FRP → Client → локальный HA. Client сам устанавливает исходящее соединение; проброс портов у удалённого дома не нужен. У каждого клиента отдельные права только на назначенный домен. Вход в сам HA остаётся обязательным.

Нужны одна wildcard-запись DNS, один wildcard-сертификат и общая маршрутизация NPM. После однократной подготовки новый поддомен появляется без изменений у DNS-провайдера. Продление внешнего сертификата выполняет NPM через DNS-01; это отдельный сертификат от внутреннего FRP TLS.

## Установка

Для центрального HA используйте только [репозиторий Server](https://github.com/Stepan-fair/ha-tunnel-server), для подключаемого HA — только [репозиторий Client](https://github.com/Stepan-fair/ha-tunnel-client). Готовые образы 0.3.1 доступны публично; GitHub-токен для установки не нужен. Старый общий репозиторий предназначен для прежних версий.

Пошаговые инструкции: [установка Server с нуля](docs/SERVER_INSTALL.md), [установка Client](docs/CLIENT_INSTALL.md). Они также доступны внутри соответствующей панели на вкладке «Инструкция». После проверки соединения включите штатное автоматическое обновление в HA.

При переходе с локального приложения меняется идентификатор и хранилище. Сначала перенесите состояние и ключи, затем переключите внутреннее имя Server в двух правилах NPM. Не удаляйте старое приложение до проверки нового и способа отката. На Client с уже подготовленным HTTP повторный перезапуск Core не нужен.

## Управление доступом и показания

Server предоставляет «Пуск», «Пауза», бессрочный доступ и смешанный календарный срок: например, 1 год 2 месяца 2 недели 3 дня 1 час 20 минут. Ручная пауза не переносит дату; пуск после истечения повторяет сохранённый срок. «Показать код» возвращает неиспользованный код, «Выдать новый код» сохраняет существующий адрес и настройки.

Server автоматически создаёт по19 сущностей HA для каждого старого и нового клиента, Client —17. Для этого включите MQTT/Mosquitto broker на соответствующем HA. Сущности показывают состояние туннеля, настоящий ответ HA, RTT, скорость и накопленный трафик, паузу/отзыв/истечение; серверные кнопки управляют доступом. Без MQTT всё доступно в панели. Сначала обновите Server, затем существующие Client на месте: старые привязки сохраняются, новые controls включаются после объявления Client поддержки.

## Для разработчика

Следующие команды относятся к исходному рабочему проекту, где есть `tools/package.py`, `tests/` и общий `shared/`. Эти инструменты разработки не входят в установочный репозиторий.

`server/`, `client/`, `shared/` — исходники, не готовые независимые Docker-контексты. Сначала выполнить:

```text
python tools/package.py --output dist/repository-0.2.0
```

Команда требует новый или пустой каталог. Полученный репозиторий содержит два самостоятельных приложения. Он не включает тестовые ключи, БД, окружение разработчика и настройки дома. Не добавляйте корневую папку исходного проекта в магазин приложений напрямую.

## Проверки

Локально: `python -m pytest -q`. Пропущенные тесты не считаются успешными.

В изолированном Linux Docker, без доступа к настоящим HA и роутеру:

```text
docker build -f tools/Dockerfile.test -t ha-tunnel-test:0.2.0 .
docker run --rm --network none --memory 512m --cpus 1 ha-tunnel-test:0.2.0
docker build --platform linux/amd64 -t ha-tunnel-server:test dist/repository-0.2.0/server
docker build --platform linux/amd64 -t ha-tunnel-client:test dist/repository-0.2.0/client
```

Сборку arm64 нужно выполнить на arm64-builder либо настроенном Docker Buildx. Docker test image использует только loopback; `--network none` достаточен после загрузки зависимостей на стадии сборки.

Публичный API регистрации работает только за доверенным NPM. Служебная политика FRP и локальная панель состояния frpc слушают loopback. Панели приложений доступны через HA Ingress с проверкой пользователя и CSRF. Подробнее: [SECURITY](SECURITY.md).
